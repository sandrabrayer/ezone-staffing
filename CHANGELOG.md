Prevention — the guards that stop bad data being created, plus the security hardening from the Phase 0 audit. **Duplicate workers**: `createWorker` now compares the new name AND phone against every existing worker, normalized the way the consumers match — padding and double spaces collapsed, bidi control marks stripped, Hebrew gershayim folded to an ASCII quote, case folded, every non-digit dropped from the phone — and refuses with `409` naming the matching rows. It is a WARNING, not a veto: only the strict boolean `confirmDuplicate:true` opens it, no truthy string does, and the confirmation is written to the audit log so a duplicate is always a deliberate act with a name on it. The same normalization runs in the browser on every keystroke of both fields, so the inline warning and the server's refusal always agree, and the warning states the real cause: a second house is a second assignment, not a new worker. **Transfer**: `moveAssignment` no longer rewrites the `house` cell in place, losing the history. It now ENDS the old placement — frozen into ArchiveV3 with `termination_date` = the day before the transfer and reason `מעבר תפקיד` — and STARTS a new assignment at the target on the same terms with the same `workerId` and the new appended `effective_from` set, truncates any absence at the house being left, and removes the old live row LAST so a failure leaves the original placement intact. The two placements tile the month exactly, so with the Phase 1 engine a mid-month transfer costs ONE month of salary split across two houses. The new placement has a new assignment id, so the UI reconciles from the server rather than patching locally. **Termination**: a reason is now REQUIRED — an omitted one becomes the explicit `לא צוין`, which is in the dropdown, so "no reason" is a choice on the record rather than a blank cell; `אחר` requires detail; the confirmation says what happens to the money, since a future date keeps the cost accruing until then; and it is IDEMPOTENT — an assignment that already has an archive row is refused with `409` and the existing archive id, closing the route to a cost counted twice. **Absences — a real bug found while building this**: the stored status was derived as `active(...) ? 'active' : 'ended'`, so a NOT-YET-STARTED absence was stored as `'ended'`. Two consequences: the overlap guard required `status === 'active'`, so two overlapping PLANNED absences were both accepted and the same leave recorded twice; and a planned absence appeared nowhere in the UI. Status is now `future` / `active` / `ended`, derived from the dates on every read, and the overlap guard compares DATES and ignores status entirely. Unstaffed positions — an absence row with no worker — stay exempt, because two unfilled slots at one house is a real situation, and get their own visually distinct list: "nobody is in this slot" and "this person is away" are different facts. The house view now has four lists — active employee absences, unstaffed positions, future, history — and a future absence can be cancelled but not "ended". **Coverages**: six columns APPENDED to the end of the tab — `replaced_assignment_id`, `role`, `shift_count`, `approval_status`, `approved_by`, `cancelled` — plus an idempotent save that returns the existing row instead of appending a second payment, overlap detection so one person cannot cover two places at once, unavailable-worker detection that REFUSES a coverage by someone who is themselves absent or on חל"ד / חל"ת / גמ"ח, a check that a named replaced placement is real and at the receiving house, and CANCEL-instead-of-delete so the row and its history survive. A legacy row with no approval cell reads back as `approved` and not cancelled — blank is never `pending`, which would look like a backlog Moran never created, and never cancelled, so nothing being paid silently stops. **Audit log**: a new append-only `audit_log` tab — `ts`, `action`, `entity`, `entity_id`, `field`, `before`, `after`, `reason` — one row per FIELD changed. Created on first use, never read by any feed, and BEST-EFFORT by design: `auditLog_` never throws, because a logging failure must not fail Moran's save. **Security** (`server.js`, `lib/auth.js`), closing audit findings A3–A6: escalating brute-force lockout — 8 wrong PINs in 15 minutes locks the IP, each further lockout doubling to a 24-hour cap, a correct PIN clearing the counter, the correct PIN refused while locked out, `Retry-After` set, a byte-identical 401 body for any wrong PIN length, and the attempt map bounded at 5,000 keys evicting oldest-first; Monthly cost engine — the selected month now drives the numbers, not just the label. **The bug** was not the month picker: the frontend already passed the selected month to every total and to the budget lookup. The month was thrown away by the calculation. `monthlyAssignmentCost()` in `lib/calc.js` takes NO month argument at all — fixed types returned a constant and hourly / per_session returned the constant estimate unless a `monthly_actuals` row existed for that exact `(assignmentId, month)`, so with no actuals uploaded every month returned byte-identical numbers. `startDate` was read by no cost function whatsoever, so a worker starting 2026-12-01 was billed in full in September. Termination and coverage extras were evaluated against `today` rather than the selected month. Nothing was prorated. **The fix** is `lib/cost-engine.js`, one pure function — `costForMonth(workers, assignments, absences, coverages, budgets, month, { archive, monthlyActuals, prorationMethod, leaveProration })` — that is now the ONLY place in the app where a rate is multiplied by a count. [3.0.0] — 2026-05-25 — Workers + per-house assignments + absence/coverage split
Major data-model redesign. The v2 "employee at a house" abstraction is replaced by worker × assignment — one worker can hold an assignment at multiple houses, each with its own role, employment type, and cost terms. The v2 coverage event (a single row mixing absentee + helper + bonus) is split into a normalized absence + coverage pair, so an absence can have zero, one, or many coverages, and coverage records survive the absence's end as audit history.
Core principle
A worker is an identity (name + notes). What they cost and where they work lives on their assignments — one row per (worker × house) pair. Cost is computed per-assignment per-type, never auto-split. When an absence is logged, it carries the house the worker is absent from; any coverage payment accrues to that house, not to wherever the covering worker comes from.
Cost attribution contract (v3)
```
assignmentCost(a)         = per-type:
                              full_time      → salary
                              part_time      → salary × pct/100
                              hourly         → hourlyRate × estHours
                              per_session    → sessionRate × estSessions
                              fixed_retainer → retainerAmount

houseAssignmentsCost(h)   = Σ assignmentCost(a) for a where a.house = h
coverageExtra(h, today)   = Σ c.extraPayment for c where c.absence.house = h
                            AND c.absence is active(today)
pendingHouseCost(h, today)= Σ frozen-cost over archive_v3 where house = h
                            AND terminationDate > today
houseTotal(h, today)      = houseAssignmentsCost(h)
                          + coverageExtra(h, today)
                          + pendingHouseCost(h, today)
networkTotal(today)       = Σ houseAssignmentsCost over all houses
                          + Σ coverageExtra over all active absences
                          + Σ pendingHouseCost over all houses
```
Each per-house assignment cost counts in exactly one house total (the assignment's own `house`). A worker with assignments in two houses contributes a cost line in each, with no double-counting. Coverage extras stack on top of the absent worker's house — independent of where the covering worker comes from. Pending terminations continue contributing until `terminationDate` arrives; on that day the archive row stops counting, matching the v2 semantics.
Data model
The Sheet now has five new tabs, all created idempotently by `setupSheetsV3`:
`workers` — `id | name | notes | created_at`. One row per person. The id is reused as `worker_id` everywhere (legacy migration reuses the v2 `employee_id` verbatim, no `w` prefix).
`assignments` — `id | worker_id | house | role | role_detail | employment_type | salary | pct | hourly_rate | est_hours | session_rate | est_sessions | retainer_amount | notes | created_at`. One row per worker × house. Each row carries its own per-type terms.
`absences` — `id | worker_id | house | start_date | end_date | reason_type | reason_detail | notes | status | created_at`. `house` is the house the worker is missing FROM (= "house needing coverage" in the UI). `status` is a hint; date math is the source of truth, and the reader lazily corrects stale `active` rows past their end date.
`coverages` — `id | absence_id | covering_worker_id | providing_house | extra_payment | notes | created_at`. Many-to-one against absences. The effective date range of a coverage is its parent absence's range.
`archive_v3` — `id | assignment_id | worker_id | name | house | role | role_detail | employment_type | salary | pct | hourly_rate | est_hours | session_rate | est_sessions | retainer_amount | notes | termination_date | reason_type | reason_detail | archived_at`. [2.0.0] — 2026-05-21 — Coverage event model
Major redesign of how staff transfers are recorded. The old "move employee from house A to house B" model is replaced by a temporary-coverage model.
Core principle
Every employee has one home house. Their base salary always stays attributed to the home house. Transfers between houses are always temporary coverage events with an optional bonus paid to the helping employee. Base salary is never double-counted.
Cost attribution rules (contract)
```
homeCost(house)    = Σ (employee.salary × pct/100) for employees living here
hostBonus(house)   = Σ event.bonusAmount  where host_house = house AND active(today)
houseTotal(house)  = homeCost(house) + hostBonus(house)
networkTotal       = Σ homeCost(all houses) + Σ active bonuses

active(today)      ⇔ start_date ≤ today ≤ end_date     (inclusive)
```
Base salary appears in exactly one house total (the home). Bonuses appear only while active, only in the host. `status` in the sheet is a hint — date math is the source of truth, and the backend lazily corrects stale `active` rows to `ended` on every read.
Data model
House tabs (`ramot`/`asher`/`ofroni`/`rehab`): added column 7 `role_detail` for role specialization. Employees stay in their home tab permanently.
New `events` tab: `id | employee_id | employee_name | home_house | host_house | start_date | end_date | reason_type | reason_detail | covers_employee_id | bonus_amount | status | created_at`.
Legacy `history` tab is kept untouched as a backup. Run `migrateHistoryToEvents()` in Apps Script once after deploy to copy every legacy row into `events` as a single-day `ended` event.
API changes
`moveEmployee` action — removed.
`startCoverage` — new. Server rejects overlapping active events for the same employee (HTTP 409) and rejects same home/host.
`endCoverage` — new. Sets `end_date = today` (if still in future) and marks `status = 'ended'`.
`/api/data` response shape: `{ houses, events }`. The `history` key is gone.
`addEmployee` / `updateEmployee`: `role` is constrained to a closed set of 9 dropdown values; `roleDetail` field added (required when `role === 'אחר'`).
